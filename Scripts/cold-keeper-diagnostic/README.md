# Cold keeper hosted diagnostic — preparation only

This packet makes the accepted source001 instrumentation executable on hosted macOS. It preserves exact Core73ac6c2/treec32f882 plus diagnostic.patch, the unchanged probe, and the existing GuardedRunner byte-for-byte. It does not contain a new process supervisor. The source, parser and workflow are prepared; native compilation, execution, network retrieval and publication have not occurred.

Install this directory as `Scripts/cold-keeper-diagnostic` and its workflow as `.github/workflows/cold-keeper-diagnostic.yml` in the qualification repository after parent review. Set only SOURCE-READY.json executionAdmitted to true for an explicitly admitted installed copy. INPUTS.json authenticates all executable harness/overlay/workflow inputs; the admission document binds that exact input hash. Original preparation remains immutable. Workflow bootstrap fetches the exact workflow commit into a new `$HOME/localdev` root under a five-minute GitHub step limit. Subsequent Core fetch and every source/build/runtime child use the existing process-group guard. The raw free/packet guards cover the entire task root, including fetched repositories. Bootstrap precedes availability of that guard; its archive is limited to the exact scripts directory and is authenticated before Core fetch. No local execution is implied by this packet.

The fixed stage commands are:

```
python3 packet/fetch-core.py --root "$TASK_ROOT"
python3 packet/harness/run.py prepare --repo "$TASK_ROOT/core-objects"
python3 packet/harness/run.py configure
python3 packet/harness/run.py build-off
python3 packet/harness/run.py build-on
python3 packet/harness/run.py run
```

Preparation exports874 tracked baseline files using git archive, verifies every byte and the exact commit/tree, then installs only the two reviewed diagnostic postimages. Both arms use that same authenticated875-file source. Fresh independent OFF/ON CMake directories inherit the same Xcode compiler, macOS SDK/platform SQLite, macOS14 deployment floor, -O3 -DNDEBUG -g0 and single compiler job. There is no package resolution or native dependency download. The probe TU is syntax-checked with its actual effective compile flags before the fresh build. Fourteen actual TUs per arm—twelve Core, one bundled sqlite-vec and the probe—must all meet the arm's uniform optimization/macro conditions. No bridge/SDK or unrelated test target is built.

Each arm's proof joins every actual TU source/object, both complete archive member inventories and member bytes, direct linker inputs, Darwin linker-map object membership, SDK import stubs, final binary and otool linkage. All Core/archive members are owned O3 inputs; Apple SDK `.tbd` imports are classified separately. Unexpected compiled objects, archives, link-map inputs or a missing runtime SQLite import fail acceptance. Toolchain and SQLite header/stub identity are recorded and checked again. This is not a claim of hashing every transitive external SDK header. Binary/archive/object/map/proof hashes are checked against the accepted build result before and after runtime. Source and harness hashes are checked again at every terminal acceptance.

Bounds remain raw free>=12.5GiB and total task root<=512MiB; compile logs<=64MiB and each sample log<=64KiB. Each build child has a1200s ceiling including syntax-first and proof generation, with a1355s outer stage for source authentication and cleanup. The schedule is exactly OFF, ON, OFF, ON, OFF, ON. Each process receives a new SQLite path, seeds100 deterministic rows, destroys the seed owner, and opens the measured owner before the interval. The first keeper and actual Core page query are timed, then a separate warm-pool sample runs. Both validate all100 integer/string/double values outside the timer. The unchanged probe validates ON recorder lifetime and branches; the parser independently requires exact19 cold/15 warm records, successful endpoints, monotonic clocks and correct pool facts. Source-derived wrapper SQL counts are cold8 (four constructor pragmas, clamp, BEGIN, schema pin and page query) and warm3 (BEGIN, pin and page query); the Swift belt/data-version query is outside this C++ recipe. SQL mismatches fail instead of being normalized.

A process is accepted only after its guard proves leader reaped and process group absent without cleanup signals/errors. Its verified closed main/WAL/SHM bytes are hashed into an immutable sample receipt before successful fixture removal. Failed fixtures stay intact. Raw stdout, group receipts, source/build identities, phase records and every elapsed time remain in the uploaded packet. No successful sample is discarded as an outlier.

ANALYSIS.json reports cold and warm separately: three paired ON/OFF outer-time ratios, raw times, min/median/max, each phase interval, acquisition residual and caller residual. It does not invent a duration for warm's absent constructor. Three pairs are a mechanism check and perturbation warning, not a stable p95 estimate. Cold means the first keeper on an already-open owner, with ordinary seeding/OS-cache warmth. Shared hosted hardware is not an isolated-load or thermal-controlled environment. Guard filesystem/resource sampling and scheduler competition can perturb these short samples; that overhead remains present in both arms and is not subtracted. macos-14 may provide a different SQLite/Xcode runtime than earlier macOS26 measurements, so record the actual versions and make no cross-graph latency comparison. These results cannot establish frozen Swift Read100 performance, bridge/hydration cost,600 live-scalar cost or a2x improvement. No ordinary-reader transfer or prewarming is implemented.
